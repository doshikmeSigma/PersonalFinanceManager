# Конституция проекта PersonalFinanceManager

Нерушимые правила. Любой код, противоречащий им, отклоняется.

## I. Спецификация первична
Код пишется только под существующее требование из `spec.md`. Новое поведение
сначала описывается в спецификации, затем в плане, затем в задачах, и только
потом реализуется.

## II. Прослеживаемость
Каждая задача в `tasks.md` ссылается на идентификатор требования (FR/NFR).
Каждый коммит решает одну задачу. Коммит, не соответствующий ни одной задаче,
не допускается.

## III. Слоистая архитектура
route → service → repository → SQLite. HTTP-слой не содержит SQL,
слой данных не знает о HTTP. Бизнес-правила живут только в service.

## IV. Деньги — целые числа
Суммы хранятся в минорных единицах (копейки, центы) как INTEGER.
Числа с плавающей точкой для денег запрещены на всех слоях.

## V. Единый контракт API
Успех: `{ "data": ... }`. Ошибка: `{ "error": { "code", "message", "details" } }`.
Иных форматов ответа не существует.

## VI. Безопасность по умолчанию
Пароли — только bcrypt-хеш. SQL — только параметризованные запросы.
Входные данные проходят валидацию схемой до обработчика.
Секреты не попадают в репозиторий; в репозитории лежит только `.env.example`.
Хеш пароля никогда не покидает сервер.

## VII. Данные пользователя изолированы
Каждый запрос к данным фильтруется по `user_id` из токена. Доступ к чужим
записям невозможен на уровне репозитория, а не интерфейса.

## VIII. Миграции идемпотентны и необратимы
Применённые миграции не редактируются. Изменение схемы — новая миграция.
Повторный запуск мигратора не изменяет состояние базы.

## IX. Mobile-first и совместимость
Интерфейс проектируется от 360px. Поддержка Chrome 60, Firefox 55, Edge 79,
Safari 12 обеспечивается транспиляцией сборки, а не отказом от современного
исходного кода.

## X. Переводы не искажают статистику
Перемещение между собственными счетами не является ни доходом, ни расходом
и исключается из всех агрегатов доходов и расходов.
